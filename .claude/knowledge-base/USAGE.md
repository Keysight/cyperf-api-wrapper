## Quick Start

| Command | What It Does |
|---------|-------------|
| `/explain {component}` | Explain any part of the `cyperf` SDK — a generated `*Api` operation (e.g. `SessionsApi.create_sessions`), a generated model, or one of the hand-written layers (`cyperf/utils.py` TestRunner, `cyperf/dynamic_model_meta.py` DynamicModel) — tracing what it actually does against the CyPerf controller |
| `/review` | Review staged changes against the project's conventions, scoped to the small hand-written surface (`cyperf/utils.py`, `cyperf/dynamic_model_meta.py`, targeted patches in `api_client.py`/`configuration.py`/`exceptions.py`, `samples/*.py`); generated files under `cyperf/api/`, `cyperf/models/`, and `docs/` are excluded by default |
| `/exec-plan {task}` | Create a step-by-step execution plan for changes such as adding a new sample script or extending `TestRunner`, flagging the scenario-zero test-framework gap (pytest collects 0 tests) along the way |

## Scenario Examples

### Understand a Component

**Task**: You need to understand how an end-to-end test run is actually driven through the SDK, e.g. before adding a new convenience method to `TestRunner`.

**Run**: `/explain TestRunner.wait_for_test_end`

**What happens**: The explain skill locates `wait_for_test_end` in `cyperf/utils.py`, traces its 0.5s poll loop calling `SessionsApi.get_session_test(session_id=...)` (`GET /api/v2/sessions/{id}/test`) until `status=='STOPPED'`, and surfaces the wider chain it belongs to — `parse_cli_options()` → `TestRunner(...)` → `create_session_by_config_name()` → `start_test()` → `wait_for_test_end()` — as demonstrated end-to-end in `samples/sample_udp_streaming_run.py`.

### Review Changes

**Task**: You've modified `cyperf/utils.py` (e.g. touched `set_prisma_airs_params` or added a new `TestRunner` method) and want to catch issues before committing.

**Run**: `/review`

**What happens**: The review skill checks your staged diff against the project's actual conventions — the typed `ApiException` hierarchy in `cyperf/exceptions.py` as the dominant error-handling pattern (flagging any new broad `except Exception` swallows like the existing ones in `set_prisma_airs_params`/`set_model_armor_params`), the `flake8` lint rules (`--max-complexity=10 --max-line-length=127` in CI, `--max-line-length=150` locally per `setup.cfg`), and confirms you haven't hand-edited any file carrying the `"Generated by OpenAPI Generator... Do not edit the class manually"` header.

### Plan a Feature

**Task**: You need to add a new sample script demonstrating a raw-API-style attack test run against a precanned configuration.

**Run**: `/exec-plan add a new sample script for attack test runs using the raw API style`

**What happens**: The exec-plan skill creates a fully-scoped execution plan in `.claude/plans/`, modeled on the existing raw-API interaction chain used by `samples/sample_load_and_run_precanned_config.py` and `samples/sample_attack_based_script.py` (`create_api_client_cli()` → `ConfigurationsApi.get_configs` → `SessionsApi.create_sessions` → per-model `.update()` → `TestOperationsApi.start_test_run_start` + `.await_completion()`), and explicitly calls out that there is no automated test suite to validate against — `pytest --cov=cyperf` collects 0 tests today, so verification has to be manual/functional. You review and approve the plan before any code changes happen. After completion, run `/knowledge-base:incremental-discover` to update the KB.

### Generate Documentation

**Task**: You need an accurate, human-facing description of how the `TestRunner`-based workflow differs from the raw-API workflow, since the generated `README.md`/`docs/*.md` don't cover this.

**Run**: `/document samples/`

**What happens**: The document skill reads `samples/*.py` (the only hand-written usage examples in the repo — `sample_udp_streaming_run.py`, `sample_attacks_load_and_run.py`, `sample_load_and_run_precanned_config.py`, `sample_create_save_and_export_config.py`, `sample_attack_based_script.py`, `sample_sequences_examples.py`, plus `samples/appbuilder/sample_appbuilder_examples.py`), infers the two idiomatic call styles already used, and writes/updates guidance rather than touching the generator-owned `README.md`/`docs/*.md` (443 model docs + per-API-class docs), which would simply be clobbered on the next OpenAPI regeneration.

### Deploy (Package & Publish)

**Task**: Build the `cyperf` package and publish a new version to the internal PyPI index after re-syncing the wrapper against a newer CyPerf controller OpenAPI spec.

**Run**: `/deploy pypi`

**What happens**: The deploy skill runs the same flow as `jenkins/JenkinsFile`: build inside `docker/Dockerfile`, bump `VERSION` via `sed` (keeping `setup.py`/`pyproject.toml`'s hardcoded `1.0.0` base in sync with the Jenkins-assigned build version), and — on a `release/` branch with `publish_pypi=true` — publish via `twine` using the credentials in `.pypirc`. `publish.sh`/`git_push.sh` are the local convenience-script equivalents of the same publish flow. This is packaging/publishing only — there is no runtime service to deploy; the "deployment target" is the internal PyPI index, and consumers (e.g. the `appsec-automation` regression repo) pick up the new version via `pip install`.

## When to Use Commands vs. Agents

**Use commands** (e.g., `/explain`, `/review`) as your primary interface. They delegate to skills, which launch agents as needed.

**Agents are internal** — you rarely invoke them directly. The skill decides which agent to use:

- `scanner` (haiku) for fast file searches
- `analyzer` (sonnet) for deep code analysis
- `reasoner` (opus) for complex architecture decisions
